# 换人时，怎么知道哪一件真的做完了？

场地联系人只收到一句“周末活动指引卡做好了”。文字、版式、现场摆放由三个人负责，接班人要知道先找谁。这个练习用虚构的阅读活动给出真实可打开的文件、独立复核记录和一张待办卡。全程用 Python 3.10 或更高版本的标准库，在本机离线运行。

## 第一次运行

1. 下载并解压仓库。在 `examples/handoff-check` 目录打开终端。Windows 可以在文件资源管理器中打开此文件夹，单击地址栏，输入 `powershell` 再回车。
2. 运行下面的命令。若电脑上使用 `python3`，把命令里的 `python` 换成 `python3`。
3. 用文本编辑器打开新生成的 `result.json`。逐项读 `state`（当前状态）、`reason`（判断依据）、`next_owner` 和 `next_action`（接下来谁做什么）。[样例应得到的结果](expected.json)

```sh
python -B -X utf8 check_handoff.py --input sample.json --output result.json
```

| 样例任务 | 读到的状态 | 交给下一位的话 |
| --- | --- | --- |
| 指引文字 `copy` | `verified` | 打开文字原件可看到领取、体验、归还三步。其当前文件指纹与复核人检查过的版本一致。 |
| 展示版式 `layout` | `blocked` | 排版人向场地协调者取得展示架宽高，写下来源，再清除阻塞原因并排版。 |
| 入口可见性 `onsite` | `waiting_human` | 现场人员站到入口观察，把位置和看到的内容写入现场记录。 |

`can_close` 是三项合起来能否结项，这份样例应为 `false`。命令成功只表示接班卡生成成功。重复运行时给输出改一个新名字，便于保留上次卡片。输出目录需已存在，并支持硬链接，在本机磁盘上的解压目录练习即可。

## 手动演练一次改版和重新验收

1. 复制整个示例目录，在副本里操作。打开 [指引文字](artifacts/guide.md)，把第二步改成“到入口右侧的阅读区”，保存。用 `--output revised.json` 重跑。这时 `copy` 状态为 `changed`，产物已换版，下一位是复核人 `checker`。
2. 复核人打开修改后的文字，按 [任务清单](sample.json) 的 `criterion` 核对三个地点和顺序。若新地点缺少依据，打开 [上次复核记录](reviews/guide.json)，把 `sha256` 填为新卡片里的 `actual_sha256`，把 `decision` 改为 `changes_requested`，在 `observation` 中写明哪一行有问题及所需依据。再运行一次，新卡片显示 `fix_requested` 并指向执笔人。
3. 执笔人补齐依据并修订后，由复核人重读最终版，记录自己实际检查的结果和该版指纹。现行版本满足标准才将 `decision` 填为 `approved`。用新文件名再运行，文字一项回到 `verified`。保留历次接班卡和修订记录。
4. 在副本将 `reviews/guide.json` 暂改名，重跑可见 `needs_review`。把原件暂改名则显示 `missing_file`。找回原件和对应记录即可恢复。另一人仅凭这组文件可重复整套检查。

SHA-256 是文件字节的指纹，换行或编码改变也会触发重新核验。这里使用已分工的角色代号。团队自己负责把代号交给不同的人，并保存各自提交的原始记录。工具核对代号、文件及复核内容之间的对应关系，无法鉴别人，也无法亲眼确认现场。

文本证据使用 UTF-8，可带字节顺序标记。只有空格、换行或控制符的文件，即使有相同指纹的通过记录，也要补交。工具按文本检查 Markdown、TXT、JSON、CSV、HTML、XML 和 YAML 文件。其他格式可交二进制原件，例如图片；复核人需亲自打开原件判断内容，工具只核对其文件指纹。

## 换成自己的任务

把工作放进同一份本地练习目录。负责人维护任务清单；执行人只改自己的产物；复核人另写记录。交接前保存一套一致的快照，接班人从快照重跑命令。输出卡可以重复生成。

| 清单字段 | 填写方法 |
| --- | --- |
| `goal`、`version` | 写清项目交付给谁、解决什么，保留版本号 1。 |
| `id`、`owner`、`reviewer` | 一个任务一个代号，执行与复核用两个不同的角色代号。代号以小写英文字母开头，可含小写字母、数字、短横线或下划线。 |
| `criterion` | 写复核人能观察到的事实，例如“领取、体验、归还有地点且顺序清楚”。 |
| `artifact`、`receipt` | 填目录内相对路径。产物放在 `artifacts/`，对应的复核记录放在 `reviews/`。使用内容独立的普通文件，以正斜线分隔路径。 |
| `gate` | `file` 指文件交付。`human` 指需要到场或经手的人留下实际记录，此时 `artifact` 指向该记录。 |
| `blocker`、`next` | 有明确阻碍就写具体缺什么，例如“缺展示架宽高”；无阻碍填 JSON 的 `null`。`next` 写执行人能直接做的第一步。 |

复核记录按样例填写。复核人逐项核对任务代号 `task`、执行人、自己、验收标准、关口类型 `gate` 和文件路径，再填实际读过的那一版指纹。结论取 `approved` 或 `changes_requested`，两者都写下可复查的观察。更换人员、标准、关口或文件后，需要重新复核。比如把 `file` 改为 `human`，应取得实际现场记录，原先的文件复核不能用于现场结项。缺少合格回执时接班卡显示 `needs_review`。清单中的 `blocker` 优先显示，由该任务的执行人在关键条件满足后告知清单负责人更新。`human` 项目收到现场记录后同样进入独立复核。

**接班时可直接复制的话**

> 先打开任务清单、当前产物和对应复核记录，生成一张新接班卡。告诉我哪些任务有本版依据，哪些仍要等人或等材料。每个未完成项写一句“谁，先做什么，留下什么证据”。遇到退回，附复核人的具体观察。

例子中的验证在本地完成。向外发布、向现场人员派单、客户确认或对外发送时，应由实际经手人留下对应回执，再更新项目记录。

开发者修改脚本、清单格式或预期结果后，在本目录运行下列回归检查。

```sh
python -B -X utf8 -m unittest discover -s . -p "test_*.py"
```
